# GeoBenchr

GeoBenchr is an application-centric benchmark for spatiotemporal database systems. Four application
scenarios, each with billions of GPS points, are queried with the same questions on six
systems running on a five-node cluster, and the systems are compared on speed and on whether they
return the same answers.

## Scenarios and data

| Scenario | Point table | Points | Data |
|---|---|---:|---|
| AIS (maritime) | `crossing_points` | 5.98 billion | ship positions 2024–2025, from the AIS data of the [Danish Maritime Authority](http://aisdata.ais.dk) |
| Aviation | `flight_points` | 2.70 billion | flights, generated by an LSTM model trained on air traffic data of the Deutsche Flugsicherung |
| Cycling | `ride_points` | 1.18 billion | bicycle rides in Berlin, generated on the Berlin street network from [SimRa](https://github.com/simra-project/dataset) rides |
| Geolife | `geolife_points` | 3.95 billion | user activity at venues, synthetic, drawn from the distributions of Geolife stay points |

Each scenario also has trip summary tables (one row per flight/ride/crossing with start and end) and
small reference tables (harbours, islands, coastlines, cities, counties, Berlin districts,
universities, venues). The generators are in [`data_generators/`](data_generators/README.md).

## Systems

| System | Deployment | Spatial pruning |
|---|---|---|
| PostGIS | Citus, coordinator + 4 workers | GiST index on the geometry |
| MobilityDB | same Citus cluster, one trajectory (`tgeompoint`) per trip | GiST index on the trajectory |
| ClickHouse | 5-node cluster, point tables sorted by `(h3, timestamp, id)` | H3 primary key: queries filter on the H3 cells covering the search area |
| DuckDB | single node, served over the network (quack) | point tables sorted by time, then Hilbert curve; `ST_Intersects_Extent` skips row groups by their bounding boxes |
| SpaceTime | partner-operated engine on the same five nodes | its own |
| Apache Sedona | Spark on YARN over HDFS | GeoParquet with a bounding-box column, row groups skipped by their statistics |

Every system uses its own native way to narrow a spatial search. ClickHouse is the only system for
which we define functions of our own (the H3 cell covers); see
[`benchmark/results/clickhouse_additions.md`](benchmark/results/clickhouse_additions.md).
SedonaDB is benchmarked separately with [`benchmark/sedonadb.ipynb`](benchmark/sedonadb.ipynb).

## Queries

48 read queries, 12 per scenario. Six of them are the same in every scenario; the other six are
specific to it.

**Same in every scenario** (on that scenario's point table):

| Query | Type | Question |
|---|---|---|
| `SpatialBBox` | spatial | points inside a rectangle covering 1–5 % of the dataset's area |
| `kNN` | spatial | the k nearest points to a location |
| `timeInterval` | temporal | ids with points in a time interval |
| `timeAggregation` | temporal | points per id and hour in a time interval |
| `spatioTemporalRange` | spatiotemporal | ids with points in a region and a time interval |
| `IDsInsideRegion1Andsecond_region` | spatiotemporal | ids that visit two regions in the same period |

**Specific to each scenario:**

| Scenario | Queries |
|---|---|
| AIS | `crossingsAroundHarbour`, `HarbourActivityInPeriod`, `countActiveCrossingsNearIsland` (whole history, no time filter), `islandOrCoastLineCrossingsInPeriod`, `CrossingsActiveAtGivenHourOfDay`, `busiestDayInWeekPeriod` |
| Aviation | `countFlightsInCounties`, `flightsInCountyInPeriod`, `flightClosestToPoint`, `CityActivityAtInstant`, `FlightsAtNightInPeriod`, `FlightsAtLowAltitudeInPeriod` |
| Cycling | `countRideInDistrict`, `CountRidesFullyInDistrictRadius`, `RidesPastOrToUniversityInPeriod`, `AverageUpdatesPerRideInDistrictInPeriod`, `RidesDuringRushHourInPeriod`, `RidesAcrossMultipleHours` |
| Geolife | `ClosestRestaurantToPoint`, `CountPOIsByTypeInRegion`, `UniqueUsersPerHourInRegionInPeriod`, `SlidingWindowActivityInRegionPerMinuteWithNonZeroID`, `FirstAndLastActivityInPeriod`, `AverageDailyActivityPerUserInPeriod` |

Every query's description and parameters are in [`docs/query-catalog.md`](docs/query-catalog.md);
each scenario's queries, in every system's dialect, are defined in `benchmark/configuration/<scenario>/config/combinedBenchConf.yaml`.

**What differs between systems:**

- Every system runs its own translation of each query (PostGIS SQL, MobilityDB on trajectories,
  ClickHouse SQL, DuckDB spatial SQL, SpaceTime SQL, Spark SQL with Sedona). All systems get the same
  parameters: a seeded generator draws them once per repetition.
- MobilityDB runs no Geolife queries: Geolife is check-in data, not trips, so it has no trajectories.
- ClickHouse has no form of `CountRidesFullyInDistrictRadius` (it has no per-group spatial aggregate).
- Distances are planar EPSG:3857 (Web Mercator) everywhere, as in PostGIS. SpaceTime measures in local
  meters, so its radii are converted per query.

## How a run measures

- **One system at a time:** before each system's run, every other benchmarked system is stopped on
  all five nodes (SpaceTime, run by its developers, stays up but idle).
- **One query at a time** from a single client; each query runs **52 times with different
  parameters**, and the first two repetitions are warm-up.
- **A timing** covers sending the query, executing it, and reading every result row on the client.
  Each system keeps one open session for the whole run, so connecting is not timed.
- **Timeout:** 600 s per query, after which the query is stopped on the server. A parameter set that
  no system finishes within the limit is left out for every system (and reported).
- **Hardware:** CPU, memory, disk and network of all nodes are sampled every 5 s.

Details, results and plots are in [`benchmark/results/`](benchmark/results/README.md).
